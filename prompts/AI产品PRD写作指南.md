# AI 产品 PRD 写作指南

> 创建：2026-06-06
> 核心理念：先写问题，再写目标，然后写流程，最后写功能

---

## 一、为什么 AI 产品经理一定要会写 PRD？

PRD 不是交差用的文档。

PRD 的本质是 **产品经理的全部思考过程**，是确保项目落地的关键。一个合格的 AI 产品经理，需要通过写 PRD 来系统化地想清楚问题，而不仅仅是拥有写文档的能力。

> 你写不清楚 → 开发看不懂 → 做出来不对 → 改成本翻倍

---

## 二、AI 产品 PRD vs 传统 PRD

| 维度 | 传统 PRD | AI 产品 PRD |
|:----:|----------|-------------|
| 重点 | 页面布局、交互流程 | AI 行为模式、不确定性处理 |
| 确定性 | 逻辑可穷举 | 存在概率性输出 |
| 异常处理 | 网络错误、空数据 | 幻觉、生成失败、用户不满 |
| 评估标准 | 是否按设计实现 | 效果指标 + 用户满意度 |
| 迭代方式 | 版本发布 | 模型微调 + Prompt 优化 + 灰度 |

## 三、AI 产品 PRD 的四维拆解法

### ① 输入侧

模型需要什么信息？以什么样式输入？

| 问题 | 例：AI简历优化 |
|:----:|:------------:|
| 输入格式是什么？ | PDF / Word / 纯文本 |
| 模型如何解析？ | 用哪个解析库？提取哪些字段？ |
| Prompt 怎么设计？ | 系统角色定义？Few-shot示例？ |
| 用户需要提供什么额外信息？ | 目标岗位？风格偏好？ |

### ② 逻辑侧

AI 的内部逻辑如何定义？

| 问题 | 例：AI简历优化 |
|:----:|:------------:|
| 优化依据是什么？ | 行业最佳实践 / HR筛选标准 |
| 如何保证建议合理？ | 输出校验规则？置信度阈值？ |
| 需要哪些约束？ | 长度限制？不可虚构经历？ |
| 是否支持用户指定优化方向？ | 偏技术 / 偏管理 / 偏行动 |

### ③ 不稳定性（AI 特有）

AI 不可控的部分怎么兜底？

| 场景 | 处理方案 |
|:----:|:--------:|
| **生成内容不符合预期** | 支持重新生成 + 提供编辑功能 |
| **出现幻觉（编造信息）** | 输出校验规则 + 显著标注非确定性内容 |
| **生成失败（超时/报错）** | 友好提示 + 重试机制 + 降级策略 |
| **用户不满意** | 反馈收集 + 手动编辑入口 |
| **相同输入得到不同输出** | 固定 seed？提示一致性要求？ |

### ④ 评估与反馈

如何度量 AI 效果？

| 指标 | 说明 |
|:----:|:----:|
| 生成成功率 | 非异常完成的占比 |
| 用户采纳率 | 用户直接使用生成结果的比例 |
| 用户编辑率 | 用户修改生成结果的比例 |
| 平均生成时长 | 用户等待的体验指标 |
| 满意度反馈 | 点赞/点踩 + 文字反馈 |
| 反复生成次数 | 每次都会再生成 n 次才算满意 |

## 四、优秀 PRD 的撰写心法

### ⚠️ 最常见的坑：让 AI 直接写 PRD

AI 太容易直接动笔。你给它一句需求，它很快就能补出页面、字段、流程、异常逻辑。看起来很完整。

但很多时候，真正缺的不是 PRD 细节。是写 PRD 前那段思考。

> **AI 不会自动停下来。它会顺着你给的那句话，把方案一路写下去。**

比如业务说：
> 订单未付款，不允许发货。

AI 很可能马上写：
> 加一个付款状态，发货前做校验，未付款就拦截，页面提示无法发货。

但产品经理真正要先问的是：
- 所有客户都一样吗？长期客户有没有账期？
- 部分付款能不能发货？超信用额度谁审批？
- 销售、仓库、财务看的状态是不是同一个？
- 退款后流程怎么处理？

问到这里，你会发现这不是一个"付款状态"的问题。
它背后可能是信用管理、应收款、发货控制、审批规则和财务对账。

---

### 写 PRD 前，先让 AI 陪你聊清楚这 6 件事

不让 AI 写 PRD。先让它陪你把事情聊清楚：

```
① 背景    — 这个需求为什么现在出现？
② 目标    — 业务想改变哪个结果？
③ 边界    — 这次做什么，不做什么？
④ 主流程  — 正常情况下怎么走？
⑤ 参与角色 — 谁发起、谁处理、谁审批、谁承担后果？
⑥ 异常情况 — 卡住、失败、反悔、冲突时怎么办？
```

> **这些没想清楚，PRD 写得越快，越危险。
> 因为 AI 会把一个还没想清楚的方案，写成一份看起来可以评审的文档。**

---

### 先写问题，再写目标，然后写流程，最后写功能

```
❌ 差：
"首页加一个AI简历优化入口，点击进入上传页面，用户上传后点击优化，展示结果。"

✅ 好（先聊清楚6件事）：
"【背景】用户上传简历后发现AI生成的描述太笼统、不够个性化。
【目标】提升简历通过率，减少用户手动逐条修改的时间。
【边界】本期仅支持PDF/Word格式，不支持照片简历。
【流程】首页入口 → 上传简历 → 填写目标岗位 → 选择风格 → AI生成优化版 → 编辑确认 → 导出。
【角色】用户发起+处理，无审批环节。
【异常】AI生成失败→重试按钮；内容不满意→手动编辑+重新生成。"
```

### 你可以不是 AI 工程师，但你要会问对的问题

| 不对的问题 | 对的问题 |
|:----------:|:---------:|
| "这个AI能不能做到？" | "衡量'做到'的标准是什么？目标是80%还是99%？" |
| "Prompt怎么写？" | "模型的输入结构是什么？输出字段规则是哪些？" |
| "如果AI生成错了怎么办？" | "生成失败的分类是什么？每类有无降级方案？" |
| "用户觉得不好怎么办？" | "不好'的量化标准是什么？编辑率 > 30%算不好吗？" |

## 五、你的 PRD-FINAL 写作清单

参照你正在做的 **PRD-FINAL**，对照这个清单：

### ✅ 基本结构
- [ ] **问题**：用户为什么需要这个功能？核心痛点一句话说清楚
- [ ] **目标**：可量化的成功标准（如：用户编辑率 < 20%）
- [ ] **范围**：本期做什么 / 不做什么 / 后续做什么

### ✅ AI 特有
- [ ] **输入侧**：格式、解析方式、Prompt 设计
- [ ] **不稳定性**：幻觉/失败/不满 的兜底方案
- [ ] **评估指标**：怎么衡量AI做得好不好

### ✅ 交互精确性
- [ ] 每个页面进入后的 **默认页面、默认按钮**
- [ ] 每个默认态的 **设计理由**
- [ ] 没有"待定""按需""适当"等模糊词

### ✅ 约束
- [ ] 只写自己确认的东西
- [ ] 不编造、不过度补全
- [ ] 不确定的写「待确认」

---

> **PRD 不是写给老板看的，是写给你和开发看的。你写不清楚，开发就猜。开发一猜，产品就走样。**
